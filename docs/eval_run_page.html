Three things before the grades

The run cannot finish on its own

It stops at step 3. The intake never asks which colleges the family is aiming at, and R1 correctly refuses to invent them — so retrieval has no target and gate_retrieval escalates. Everything below required a human to supply six target schools. This is the blocker: one intake question fixes it.

The finished plan does not name the child

The cover reads "Student name to be confirmed." The name is in the intake; R1's schema has no field for it, so it is dropped before the writer ever sees it. The writer behaved correctly — it flagged rather than invented. The critic then missed it across all 12 of its findings.

Three of eight gate verdicts were wrong

Two false failures — gate_profile tripped on the word "tier" in ordinary prose, gate_plan looked for dates in the wrong place. One false pass — gate_recs waved through a recommendation whose own escalate flag was true. The false pass is the dangerous one.

Four fixes, in order of leverage

  1. Write down the output schema for every step

    Not a style issue — the single largest cause of failure in this run. R1 returned constraints as a list where the code expects an object. R6 nested tasks one level deeper than the gate looks. R7 returned primary/alternates where the pipeline reads recommendations. Each prompt names its keys but never their shape, so every step is free to guess differently.

    Fixes both false gate failures, the false pass, one crash, and the missing name.

  2. Add two questions to the intake

    Which colleges are you aiming at — and how many hours a week can he actually give this. The first unblocks the whole run. The second is why the plan's capacity reasoning stays qualitative and the schedule can't be checked against anything.

    Unblocks step 3; lifts Plan Goals and Two Paths.

  3. Give Two Paths and Recommendations real inputs

    Two Paths needs per-school admit counts, not one corpus-wide tally. Recommendations was handed a single catalog row with no contact field. Both behaved correctly on thin input and produced thin output — that is a wiring and data problem, not a prompt problem, and no prompt edit will fix it.

    Two Paths B → A; Recommendations C → B.

  4. Tighten three prompts

    Strategy: exactly one core thread. Gap: closed category set, no counting, no fit judgments. Writer: never narrate our own inputs. These are the real prompt-quality gaps — and they are the smallest part of the problem.

    Strategy and Writer B → A; Gap C → B.

What worked

The retry mechanism works. Strategy returned 12 moves with no spike, the gate caught it, the retry with the failure as feedback came back with 6 and a spike, and passed. First time that has ever been observed.

No step invented a number. Every figure in every output traced back to something handed to it. Where data was missing, agents said so rather than estimating — Two Paths refused to fabricate a fit percentage, the writer refused to invent a name. The evidence contract is holding.

Retrieval is real. 497 admit cards across 67 students, once targets exist.

Method. Each step ran in a clean agent given only its exact prompt from prompts.py and its real input JSON — no repo access, no sight of previous outputs. Modules and gates ran as real code. Each step was then graded by a second clean agent against its rubric file, blind to who produced the output.

Caveat. This approximates a real API run; it does not measure latency or cost, and it is one run on one intake. Treat the grades as directional and the defects as real — every failure above was reproduced from actual output, not predicted.
